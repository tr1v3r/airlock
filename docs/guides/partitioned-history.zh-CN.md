# Shared 活动状态与终态历史分离

[English](partitioned-history.md)

Redis 和 PostgreSQL 将保留的终态结果与每次恢复调度器的活动状态分开处理。
`Driver`、`Shared`、本地准入和完整状态 `Transition` 的行为保持兼容。
自定义驱动仍可使用完整快照；`TransitionPartial` 是供原子维护权威历史元数据的存储使用的可选底层接口。

## 原子性与保留窗口

部分状态必须包含全部排队、持有记录，以及目标请求的完整现有记录；即使目标终态已经可以回收，也必须加载。
与完整转换一致，先检查请求身份冲突，再回收历史。省略终态的数量必须精确，不包含后端求值时刻已经可以回收的记录；
最早省略终态的回收时间约束提交窗口。回收时间为 `max(Finished + Retention, SubmitUntil)`。

活动记录到期、释放或取消、保存终态、复用容量、队列调度和资源元数据，在同一个资源串行化边界内原子提交。
没有异步双写历史，也不自动重放结果不确定的写入；超时或响应丢失仍不能证明后端没有执行。
`MaxRecords` 继续同时限制活动记录与保留的终态记录。

普通操作不再传输、解码或恢复无关的未到期终态，但一次操作仍可能回收全部已到期历史。
本步成本与活动状态及到期历史有关，并没有固定 GC 时间预算。活动状态仍需恢复和校验，续租没有绕过维护与公平调度直接改一行。

## 存储与部署

Redis 的 `active` 字段只保存活动快照，`r:*` 保留逐请求投影，同槽 `stateKey:history` 有序集合保存终态回收时间。
`state` 字段发布 v2 标记，提交仍原子检查更新锁 owner 与 CommitWindow。
多命令发布前先标记 incomplete，使中途运行时错误不能把部分迁移结果暴露为有效状态。

PostgreSQL 保留请求表，增加有索引的回收时间和资源精确计数，普通操作只加载活动行和目标终态行。
修改与按索引回收仍在同一个事务、同一资源行锁内完成。
在受控部署阶段执行 `EnsureSchema`；表结构和索引 DDL 可能阻塞写入。

现有 v1 资源会在首次提交的转换时全量读取、验证并迁移，包括维护或返回业务错误但产生非空 next 的转换；这次操作仍与历史量相关，可能需要更大的部署时间预算。
后续修改使用分离格式；只读查询可能让 v1 资源暂时保持未迁移。

首次 v2 修改前升级全部写入端，串行执行结构变更。旧完整状态写入端不能安全操作 v2，应明确失败。
回滚旧二进制不等于降级存储格式；降级需要应用自行组织停写、离线验证转换，本变更不提供该工具。
不能通过删除资源、缩短历史保留窗口来强行回滚，否则可能遗忘 owner、占用容量或幂等结果。

## 完整性边界

驱动校验迁移记录、写入内容、活动记录、目标终态及索引／计数的一致性检查。
每次续租不再校验所有未访问终态的完整载荷，因此应禁止绕过驱动修改存储；完整数据审计应独立于热路径进行。
历史摘要并不是全部载荷的密码学完整性证明。

Redis 发布停在 incomplete 时保持不可用。应停止相关写入端，并停止或排空其活动业务后再恢复，核查完整记录、索引和不确定的业务结果，
不能只删除标记、重建空资源或盲目重放失败操作。后端持久性限制以及应用的租约／fencing 前提继续遵循各驱动文档。
