# 本地优先级：选择机会、入口隔离与队首保护

状态：当前功能分支的实现决定；不表示已合入 `dev` 或发布。完整状态机见
[本地调度契约](../proposals/002-weighted-scheduling.md)，比较证据见
[实验报告](../proposals/002-priority-experiment-results.md)。

## 目标与 API

同一个进程内，让高优先组在竞争时获得更多准入机会，同时使已入队的低组请求最终能够推进。
保留 `Acquire`、`AcquireFor`、`AcquireN`、`AcquireNFor` 以及四个 `TryAcquire` 的签名。
所有入口共享同一容量池，权重仍表示一次原子获取的令牌数。

新增可选的 `Config.Priority *PriorityPolicy`：组配置包括 `Name`、`Turns`、`MaxQueued`；
`DefaultGroup` 指定默认租户与未映射租户的归属；`TenantGroups` 是静态可信映射。
`Priority == nil` 完全保留单组租户轮转，不要求简单用户先学习优先级。
配置启用时组列表非空、组名非空且唯一，正份额按顺序不递增、总和不超过 1024；
组等待上限非负且总和不超过全局上限；默认组及映射目标必须存在，映射不能用空租户键。
非法配置返回 `ErrInvalidConfig`。

## 1. 更多选择机会，不采用严格优先

`8:3:1` 展开为 `HHHHHHHHMMML`。游标跨调度调用保留；空组跳过，不积累信用。
组内租户轮转，租户内 FIFO。无竞争时即时获取不消耗选择槽位，因此配置不是流量配额或速率限制。

严格优先会使持续高组流量永远挤走低组；这里用正份额保留低组机会。代价是即使高组仍在等待，
轮到低组时仍可能先授予低组。高组不能抢占已有 Permit，也没有绝对更短的等待时间保证。

## 2. 大请求保护跨越组优先级

容量为 5、已占 4，轮到低组请求 4 个令牌时，剩余 1 个暂时闲置；后来高组请求 1 个也不能越过。
已选请求持续保护，直到全部容量足够或取消。旧持有者最终释放后，大请求能够获得完整权重。

这防止持续小请求消耗所有释放空间，代价是全局队首阻塞与容量闲置：低组大请求也能延迟高组。
若业务需要高组延迟隔离，应评估独立 limiter、组固定容量加借用，或者明确定义的有限绕过策略；
不能无限放行高组又保留大请求不饿死的承诺。本阶段不引入 aging、抢占或自动过期。

## 3. 按选择次数公平，不按资源消耗公平

全组持续非空且没有已选请求取消时，完整周期才是 `8:3:1` 的成功授予比例。
已选请求取消仍消耗其组槽位和租户机会；未选请求取消不消耗机会。被拒绝的请求也不消耗机会。
这是**选择次数**公平，不是令牌数或 token-time 公平。例如高组一次拿 1 个令牌，低组一次拿 20 个，
低组即便次数少也可能消耗更多资源。若需要资源份额，应另定义成本度量，不直接改写本契约。

较短的业务执行超时可以减少配合取消的任务占用，但不能单独保证资源公平。
申请 context 只控制等待，成功后取消不会撤销 Permit；任务实际停止使用受控资源后才能释放。
Airlock 不执行任务、不自动重试；排队失败或业务失败后的重试、退避和幂等由调用方负责。
若需要更严格的资源约束，应另评估组执行占用上限或资源成本调度。

## 4. 独占等待额度，代价是不能互借

组 `MaxQueued` 只限制等待请求数，不预留令牌；已选但未授予的 protected 请求仍占等待额度。
各组额度总和不超过全局 `MaxQueued`，全局未分配的差额也不会自动共享。
高组满时即使低组额度空闲，高组仍被拒绝。这保留低组的等待入口，代价是过载下可能提前拒绝请求。

检查顺序固定为全局 `ErrQueueFull` → 组 `ErrGroupQueueFull` → 租户 `ErrTenantQueueFull`。
单租户等待额度仍独立生效。低组自身或同组其他租户仍可填满低组，因此不是对每个新请求的入队保证。
组额度为零只禁止等待；没有等待者且容量足够时，任何组仍可即时获得完整权重。

## 5. 静态可信映射，避免请求自行选择优先级

`New` 深拷贝组切片和租户映射；实例存活期间修改原配置不生效，不支持动态迁组或修改份额。
默认租户与未映射的显式租户都走默认组，但仍是独立租户，不合并 FIFO 身份。

没有 `Acquire(..., priority)` 参数，也不在锁内执行用户分类回调。上层必须先认证并提供可信租户 ID；
静态映射不是认证机制，无法阻止调用方冒充高组租户或伪造大量身份。
需要在线调整时，后续应明确排队中请求归属、游标与额度变更语义，再增加 API。
直接新建实例替换旧实例也有代价：旧 Permit 未释放前，新旧实例可能同时放行并突破原预算；
切换需要排空旧实例，或另行设计跨代共享预算。

## 6. 单锁保持状态一致，接受内部操作串行化

每个 Airlock 实例用一把互斥锁保护容量记账、三层队列、组游标、受保护请求和统计快照。
申请、取消、释放在同一锁内完成状态转换，避免部分分配、重复扣减以及取消/授予竞争导致泄漏。
等待者阻塞在 channel 时不持有锁，业务任务执行也不持有锁，因此业务仍按获准容量并发运行。

代价是大量 goroutine 同时申请、释放、取消或读取 Stats 时会竞争该锁。Release 在锁内执行
调度，一次可能授予多个请求；每次组选取也可能扫描最多 1024 个槽位，因此不能把临界区
视为固定成本。TryAcquire 虽不等待容量，也需要获得这把锁，并不是 wait-free。

当前选择先保持一致的状态机。是否拆锁，应在目标负载下测量 mutex/block profile、临界区
持有时间和申请/释放开销后再决定；现有比较实验没有单独证明锁在高并发下不构成瓶颈。
拆锁需要重新验证跨组容量原子性、取消竞争和队首保护，不能只按组拆锁后保留原有保证。

## 补充：TryAcquire 与统计保持简单

所有 TryAcquire 仍要求全局没有等待者且容量足够，不能绕过其他组或受保护大请求。
它不入队、不消耗组/租户等待额度、不消耗调度槽位，不检查 context；仍需短暂取得内部互斥锁。
否则返回 `ErrWouldBlock`，不改变排队与调度状态；不要用循环 TryAcquire 替代排队。

`Stats` 保留汇总的令牌数、Permit 数、请求数和等待租户数，本阶段不增加公开按组统计。
若生产观测需要按组拒绝率/等待时间，应先定义有限维度与事件含义，避免将全局快照误作组级保证。

## 活性保证与验证范围

保证对象是已经入队、持续未取消的合法请求。前提为持有者最终释放、调度及 goroutine 持续获得执行机会、
队列有限、组份额为正且进程未崩溃。受保护请求最终能凑齐容量，有限正份额循环最终选中每个非空组，
组内轮转及租户 FIFO 则避免后来的请求永久越过先前请求。忘记 Release 会破坏进展前提。

`8:3:1` 中持续非空的低组两次选择之间最多 11 次其他组选择；这不是每个低组租户或请求的上界，
更不是毫秒上界。context 允许放弃等待，不提供完成 SLA；有界队列不等于有界等待时间。

验收覆盖饱和份额、空组跳过、取消消耗槽位、租户 FIFO/轮转、三层错误顺序、配置深拷贝、
大请求跨组保护、TryAcquire 禁止插队及并发容量守恒。比较实验用于展示严格优先的饥饿反例和
本策略的利用率代价，有限实验不证明生产 p99 或无限时间内活性；证明依赖以上前提及状态机。
