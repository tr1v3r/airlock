# 高组延迟隔离：固定容量分区及其代价

状态：方案与实验决定，使用现有 Airlock 组合；不新增公共 API，不表示已合入 dev 或发布。
相关资料：[方案契约](../proposals/003-high-priority-isolation.md)、
[实测及原始数据](../proposals/003-isolation-experiment-results.md)、
[本地优先级六项取舍](003-local-priority.md)。

## 1. 保留执行容量，接受闲置与更早拒绝

高组有准入延迟要求，仅提高 Turns 不能排除低组已运行任务和受保护大请求的阻塞。
采用两个独立实例，在总预算内为高组预留容量：实验为总量 12、高组 4、中低组 8。
两池的队列、锁和受保护队首独立。低组不能占用高组预算，高组也不能溢出到低组池。

代价是高组空闲时其容量闲置，高组自身突发时也不能借用低组容量。实测高组自身过载时，
共享池成功 63/480，分区池 19/480；只有低组负载时，吞吐由约 2136/s 降到 1482/s。
这是一项隔离与利用率的选择，不能宣传为普遍提速。实验参数不是生产容量建议。

## 2. 不借用、不抢占，保留容量才可立即使用

本阶段不让低组借用高组保留容量。允许借用后，借出的容量在低组实际停止前不能安全回收；
发送取消信号不等于任务已经退出。Airlock 只管理 Permit，不拥有工作线程或业务任务生命周期。

直接超时释放仍在使用资源的 Permit，会让新旧工作同时运行，突破真实资源预算。
若后续增加借用，应先确定可验证的退出时限或可抢占执行环境，并重新定义高组的等待承诺。
拒绝低组借用的代价正是上一节的闲置容量，本阶段明确接受。

## 3. 隔离低组依赖，不承诺高组一定成功或准时返回

独立高池仍可能被高组自己的任务占满。使用小队列、独立等待预算和明确的拒绝/降级策略，
在过载时限制积压。5ms 等待预算表示到期取消，不代表 5ms 内一定成功或精确返回。
授予与取消竞争、锁竞争及 goroutine 调度都可能让返回晚于 deadline。

因此同时评估成功等待分位数、全体返回时间、拒绝率和超时率，不能只比较成功样本 p99。
本次有 6 次超过计划 deadline 才返回成功的样本，已保留在报告中。
高组自己的服务时间、最大权重和到达率也需要业务约束，固定分区不能替代过载治理。

## 4. 申请期限与执行期限分离，失败由调用方处理

等待 Acquire 超时会出队并返回错误；成功返回的 Permit 不会因该 context 后来取消而撤销。
调用方另设业务执行期限，并确保工作响应取消、实际停止使用受控资源后才 Release。
不能启动后台任务后，仅等前台超时就提前归还 Permit。

Release 只归还容量，不表示成功或失败。Airlock 不执行、不自动重试任务；重试、退避、
幂等和降级由业务决定。代价是调用方承担生命周期管理，收益是库不会因隐式重试制造重复工作
或过载反馈。执行超时也不能单独证明按累计资源消耗公平。

## 5. 先组合实例，暂不新增统一分区 API

已有两个实例就能实现独立容量、排队与保护；示例把申请等待和业务执行分开。
本阶段没有充分证据表明统一 API 能提供额外保证，因此先保留组合方式。
代价是调用方负责可信路由、容量总和、各池统计和生命周期，避免把高组身份暴露为任意请求选项。

只有这些接入逻辑在多个真实使用方持续重复，才设计总预算校验、统一统计或配置迁移封装。
不在两个池后再加可被低组占满的共享阻塞入口，否则重新引入高组依赖。

## 6. 固定分区缩小合法权重范围，配置迁移需要排空

共享池可接受的请求，分区后可能超过目标池容量。实验中高组最多 4、低组最多 8，超限返回
ErrWeightExceedsCapacity。不会自动跨池拼凑或拆分一次原子申请；能否拆分任务由业务决定。

实例在启动时创建且不动态改容量。旧 Permit 仍存活时直接新建池并接流量，会让新旧容量叠加。
切换应暂停旧入口并排空旧 Permit，或另行设计跨代预算。前者牺牲无缝调整，后者增加一致性复杂度。

## 7. 只隔离本库准入，外部资源仍需对应治理

两个池仍可能共享 CPU、数据库连接池或下游服务。低组占满真实瓶颈时，高组即使获得 Permit，
业务完成时间仍可能变差。固定分区保证的是本库中的容量依赖边界，不是端到端 SLA。

本次任务通过 Sleep 模拟持有，有限三种 seed 不代表统计置信区间或生产 p99。是否进一步实施
连接池隔离、执行资源配额或独立服务，需要真实负载与瓶颈测量；不能由本次数据直接推出。
