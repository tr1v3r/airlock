# 决策 001：本地多令牌准入的取舍

状态：当前本地多令牌实现采用的设计决策。适用于 `AcquireN` / `AcquireNFor` 及其单令牌入口，本文不覆盖优先级分组的扩展（见[优先级决定](003-local-priority.md)）。分布式 driver 与 Shared/Lease 现已实现，契约见[决策 005](005-driver-contract.md)，不属于本文的本地生命周期。原记录日期：2026-10-22。

契约及后续设计见 [RFC 002](../proposals/002-weighted-scheduling.md)；实现见 [airlock.go](../../airlock.go)，验证见 [weighted_test.go](../../weighted_test.go)。本文记录选择理由、成本和重新评估条件，不新增 API 保证。

## 决策摘要

第一版优先保证原子获取、租户轮转和大请求不被无限插队，接受部分容量闲置，以及不同租户占用资源不相等。没有“同时获得最高利用率、最短小请求延迟、严格资源公平”的承诺。

| 当前选择 | 获得的性质 | 接受的成本 |
| --- | --- | --- |
| 保护已选队首，禁止绕过 | 大请求不会被持续到达的小请求无限插队 | 队首阻塞、空闲容量、其他租户延迟 |
| 按请求选择机会轮转 | 每个已排队租户获得轮转机会，规则简单可解释 | 不保证令牌数或令牌占用时间公平 |
| 整批获取、整批释放 | 不会为同一次申请部分持有容量，释放数量由 Permit 保存 | 不支持部分释放、追加权重和拆分凭证 |
| 单把互斥锁协调 | 容量、队列、取消和授予有统一状态转换顺序 | 高竞争时可能出现锁竞争，批量调度延长临界区 |
| 授予成功后由调用方释放 | 不会因获取 context 取消而提前回收正在使用的容量 | context 取消后仍可能返回成功，必须处理返回结果 |
| 有界队列，无自动过期 | 限制等待请求数量，不凭时间猜测工作已结束 | 无等待时长保证，忘记释放会持续占用容量 |

## 1. 大请求不饿死与容量利用率

选中请求所需令牌不足时，调度器保留该请求，暂停后续授予。选择时已经消耗租户的轮转机会；取消该请求会解除保护，但不会把轮转位置倒回去。容量完全占满时不提前选择请求。

例如容量为 5，已有一个 Permit 持有 3 个令牌：

| 事件 | 占用 / 空闲 | 结果 |
| --- | --- | --- |
| A 申请 4 个令牌 | 3 / 2 | A 被选中并等待，不占有部分令牌 |
| B 随后申请 1 个令牌 | 3 / 2 | B 不能绕过 A，2 个令牌暂时闲置 |
| 原持有者归还 3 个令牌 | 0 / 5 | 先原子授予 A 的 4 个，再授予 B 的 1 个 |

如果允许任何放得下的小请求越过 A，小请求持续到达时，释放出来的容量可能一直被填满，A 永远凑不齐 4 个令牌。当前接受全局队首阻塞（HOL）来避免这种无限插队；小请求的等待时间可能明显增加。

“不饿死”针对已经入队、持续未取消的合法请求，并依赖有限队列、已有持有者最终释放，以及调度持续获得执行机会。它不保证每个新请求都能入队，也不提供固定等待时长上界。

**重新评估条件：**混合权重负载中，“有等待者但令牌空闲”的时间和吞吐损失达到业务不能接受的程度。届时可比较有限次数绕过后保护、按组隔离等方案；必须同时验证大请求进展，不能只比较总吞吐。当前没有实现这些替代策略，也没有测得本策略的生产性能收益。

## 2. 请求机会公平与资源份额公平

每个租户内部 FIFO，非空租户之间轮转选择队首。新租户加入轮转尾部；空队列移除后重新加入也在尾部。已选请求取消仍消耗该次轮转机会，因此有取消时，选择次数也不一定等于成功授予次数。

A 每次申请 4 个令牌，B 每次申请 1 个令牌：各获得一次机会并不表示资源使用相等。即便两者权重相同，持有时间不同也会造成占用差异。当前权重只表示占用容量，不代表公平调度积分。

这适合“各租户都有机会进入”的目标，不适合作为租户资源配额、计费或令牌占用时间公平的保证。一个租户在没有其他等待者时仍可占用全部容量。

**重新评估条件：**业务明确要求每租户令牌份额或 `令牌数 × 持有时间` 份额。需要先定义计量方式、长任务成本、突发额度及补偿规则，再选择按成本调度或配额方案；仅将轮转次数改为权重扣分并不能自动得到占用时间公平。

## 3. 整批获取与接口灵活性

一次申请要么得到全部 n 个令牌，要么不占用令牌并等待/失败。不会通过循环调用单令牌 Acquire 来凑 n 个，因而避免同一次申请中的“大家各拿一部分、都等剩余容量”问题。

Permit 保存实际权重，Release 不接受数量参数，使用 `sync.Once` 保证并发或重复调用只归还一次。代价是不支持部分释放、调整权重或拆分 Permit。

这一性质不消除业务层的嵌套获取死锁：例如调用方持有旧 Permit，又等待同一 Airlock 的新 Permit，仍可能耗尽容量。应尽量一次申请工作所需全部令牌，而不是把追加申请当作已有凭证的扩容。

**重新评估条件：**存在明确的分阶段资源归还需求。增加部分释放前需要单独定义剩余权重、并发释放、拆分后的所有权和错误处理，不把这些状态隐式塞进现有 Release。

## 4. 单把锁与高竞争吞吐

`used`、凭证数、租户队列、轮转和受保护请求统一由一把互斥锁维护。容量判断使用 `n <= Capacity - used`，避免相加溢出。channel 仅通知某次申请已授予，不表示可用令牌数。

这让取消、授予、释放和 Stats 快照的顺序可判断，减少跨锁协调及记账不一致的空间。业务执行、等待 channel 均不持锁，Airlock 不启动后台 worker。

代价是所有申请/释放共用一个临界区；一次 Release 可能连续授予多个请求，队列很大时临界区也可能增长。单锁不代表没有瓶颈，换成原子变量也不能单独解决队列调度与计数的一致性。

**重新评估条件：**代表性负载的 mutex/block profile、吞吐和尾延迟显示锁竞争占据主要成本。先测量再决定是否拆锁或限制单次调度批量；修改时必须保持原子申请、通知及取消契约。现有正确性测试和覆盖率不能证明性能充分。

## 5. 取消语义与调用方责任

取消和授予竞争时，以锁内先完成的状态转换为准：取消先移除等待者则返回错误且不占令牌；授予先保留容量则返回成功 Permit，即使此后 context 已取消。

因此调用方不能仅凭 `ctx.Err()` 判断是否持有容量，必须检查 Acquire 的返回结果，并释放每个成功返回的 Permit。成功后可以选择不开展工作并立即释放，也可以将 context 传给业务代码处理取消。

授予后不因 context 取消自动释放，避免业务仍在执行时把同一容量再次分配出去。代价是“context 已取消但 Acquire 成功”属于合法结果，需要在接口文档中明确。

**重新评估条件：**若要改变取消优先级，需要作为契约变更处理，重审全部入口及竞态测试；不能把它当成无影响的内部优化。

## 6. 有界队列与等待时间、生命周期

`MaxQueued` 和 `MaxQueuedPerTenant` 按等待请求数计量，不按权重或等待时长计量。它们限制队列规模，但不是精确的内存字节预算，也不能保证某个新租户一定获得排队位置。

等待者可以用 context 放弃等待。已授予的本地 Permit 没有租约、自动过期或回收；忘记 Release 会持续占用容量，并可能阻塞受保护的大请求及其后的请求。不能用超时自动归还来假定业务已经停止。

**重新评估条件：**若需要确定的等待 SLA，需要结合工作持有时间、队列接纳和资源隔离设计；若需要跨进程故障恢复，则进入独立的 driver/租约设计，其保证不能直接套到本地 Permit 上。

## 验证与后续实验

现有测试验证权重边界、全量获取/释放、受保护请求不能被小请求绕过、取消后的轮转顺序、按请求轮转、队列单位、整数边界以及并发容量守恒。race 检测用于发现并发访问问题，不证明所有调度都不会饿死；活性依赖上述前提和状态转换规则。

后续评估策略应统一容量、到达轨迹、请求权重、持有时间和随机种子，至少报告：

- 每租户成功授予次数、拒绝数、等待分位数和最大等待。
- 令牌利用率、有等待者但令牌闲置的时间，以及吞吐。
- 大小请求分别的等待表现，取消时的进展情况，以及 mutex/block profile。

单令牌历史实验不能直接作为混合权重策略的性能结论。替代策略只有在明确改善目标指标、保留所需进展保证后，才值得改变当前实现。
