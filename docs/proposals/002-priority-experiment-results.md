# 本地优先级比较实验

状态：本地优先级功能分支的有限负载实验；不是发布性能承诺。基线为已合入本地多令牌及 TryAcquire 的 `dev`，被测新实现增加可信租户分组与 `8:3:1` 请求选择份额。

## 结论

真实公共 API 实验观察到了预期的取舍：等权竞争时，高组等待减少，低组等待增加；稀疏低组在无优先级的租户轮转下反而更快。优先级不是对每个租户的统一延迟优化。低组大请求场景中，新实现和容量不受额外限缩的两层 semaphore 吞吐接近；不能由此声称 Airlock 普遍更快或两层 semaphore 无用。

正份额和受保护队首提供的是有前提的进展契约。有限负载全部完成不能证明永不饿死；证明边界见[调度契约](002-weighted-scheduling.md)。严格优先级反例模型与运行时确定性测试用于检验选择规则，时延数字不作为 CI 门槛。

## 实验方法

- 平台：Darwin arm64，Go 1.24.13；比较依赖锁定 `golang.org/x/sync v0.16.0`。未固定 CPU 核、调度器或系统背景负载。
- 每个组合 192 个请求，容量 8，2 个租户/组；固定种子 1、2、3。预生成统一的到达、权重、持有时间、取消期限轨迹，再按相同轨迹分别运行各适配器。
- 到达间隔目标为 100 μs，真实 goroutine 启动和计时仍受系统调度影响。等待时长从 goroutine 开始调用到 Acquire 返回，不包含 goroutine 启动前的到达延迟。取消期限相对于预定到达时刻，持有期间不自动撤销已授予 Permit。
- `saturated` 是有限等权积压，不是每组无限持续饱和；首尾排空阶段不保证所有组非空。H/M/L 各 64 个请求，权重 1，持有 2–4 ms。
- `sparse-low`：H/M/L 为 136/48/8 个请求，其余同上；每 24 个到达仅 1 个 L。
- `low-large`：各组 64 个请求，H/M/L 权重为 1/2/8；L 持有 6 ms，H/M 持有 2–4 ms。
- `cancel-mixed`：各组 64 个请求，权重随机 1–4，约三分之一附带 3–10 ms 期限，持有 2–4 ms。成功/取消结果允许受库取消契约及执行时序影响，不强行要求各实现相同。
- 队列预算刻意不构成瓶颈：Airlock 全局 576、每租户 192；优先级模式每组 192。192 个总请求不会触发预算拒绝。semaphore 原生队列上限与组额度为 **不适用**，不偷偷叠加组调度器；本实验不比较过载入口隔离，隔离由契约测试验证。

| 名称 | 实际执行路径 |
| --- | --- |
| fifo | 单个 `semaphore.Weighted.Acquire(ctx, n)` |
| nested | 先租户级再全局 `Weighted.Acquire(ctx, n)`；每个租户容量也为 8；全局失败回滚本地名额 |
| airlock | `AcquireNFor(ctx, tenant, n)`，`Priority == nil` |
| priority | 相同公开入口，可信租户映射到 H/M/L，轮转份额为 8:3:1 |

nested 不额外加入公平调度。等待全局名额期间会占住租户名额，因此不同租户进入全局队列的速度不同；它自然限制同租户在全局队列中的请求，能改善部分负载。每租户容量设为全局容量，避免用偏小固定上限制造利用率劣势。

## 指标边界

原始结果逐 seed、逐组保留 granted/rejected/cancelled、前 48 个返回成功的数量，以及成功请求等待 p50/p95/p99/max。分位数取排序后下标 `floor((N-1)*p/100)`；稀疏 L 每次只有 8 个样本，因此这些是样本分位数，尤其不是生产 p99。取消等待不混入成功等待分布。

表中吞吐是成功请求数 / 从首个到达到最后一个任务释放的总时长；利用率代理是调用方观测的已返回且尚未开始 Release 的令牌时间 / (容量 × 总时长)。`idle+pending` 代理是至少一个 Acquire 调用尚未返回、且调用方可见占用小于容量的时间比例，**不是空闲令牌时间比例**。它包含通知/唤醒、调用返回调度、两层 semaphore 的本地等待，以及真实队首阻塞；不能精确分离成内部 HOL 时间。代理计数使用短暂互斥锁，实验本身有观测开销。

公开 API 看不到内部请求被选择的时刻；成功返回顺序也可能被 goroutine 调度重排。因此不从负载日志推导“最长选择间隔”，而在下方确定性选择模型和运行时契约测试中验证。`first48` 只辅助观察有限窗口倾向，包含最初即时授予，不能拿它验证精确 8:3:1。

## 严格优先级反例与选择间隔

独立确定性模型从 H/M/L 各一个等待请求开始，每次授予后立即补充同组请求，使三组一直非空，执行 1200 次选择：

| 策略 | H/M/L 授予 | 同组两次选择之间最多其他组选择数 H/M/L |
| --- | --- | --- |
| strict | 1200/0/0 | 0 / 不适用 / 不适用 |
| 8:3:1 | 800/300/100 | 4/9/11 |

严格优先级每一步都重新看到 H 非空，最初的 L 从未被选择；按此补充规则可无限延长轨迹。这是策略反例，不代表 semaphore 自带严格优先级。模型也不模拟容量、取消或 goroutine 调度；真实实现的全饱和份额、空组跳过、租户 RR、已选请求取消消耗槽位、受保护大请求及容量守恒由本地确定性/并发契约测试覆盖。11 是持续非空低组的组级选择间隔；不是某个低组请求的等待时间或租户级界限。
