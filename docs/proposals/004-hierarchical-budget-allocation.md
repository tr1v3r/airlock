# 分层预算分配器方案

状态：设计提案，未实现，分两阶段交付（见"阶段划分"）。本文的 Budget/Allocator
状态与 API 均为拟议契约，不表示现有 Shared 已具备这些能力。本 PR 只改设计文档，
不改公共 API 或运行时；不依赖合并 #61，也不授权合并 #61/#62。实现原型及是否
推进须另行评审。

## 0. 阶段划分

**阶段一（先行，可独立交付）：预算块租约 + 本地准入的最小实现。**

- 构件：现有 `Shared`（AcquireN/Renew/Release/Resize）直接作预算池后端；
  网关持有离散面额的 chunk 租约；本地 Airlock 做请求级准入；控制循环沿用
  §10 的骨架（按加权占用、峰值与队列调目标）。复用 §2 的结构与 §4 的整块
  面额约定，不引入 §3/§5–§9 的账本状态机、幂等 Seal、隔离与恢复机制；
  §12 的反例轨迹在阶段一不作要求。
- 适用契约（必须满足其一并在部署文档声明）：
  1. 被保护资源自执法硬上限（如自有 DB 连接池、下游自带准入）——预算层
     只做公平与削峰，超发被真实资源挡住；
  2. 执行者可改造：可信完成信号直达预算池，或存在硬执行上界 D；
  3. 业务显式接受崩溃后有界超发（超发窗口 ≤ LeaseTTL × 崩溃网关持有量）。
- 边界（阶段一不成立即为阶段二场景）：网关崩溃后 TTL 回收的 chunk 可能仍被
  其在途上游执行占用。在上述契约下这只是性能损失，不是完整性破坏；执行
  不可观测的第三方配额（DS/OpenAI 类）不适用阶段一。
- 验收：全网关准入并发 ≤ 池容量；TTL 回收后可再获取；work-conserving；
  闲置两周期归还；后端不可达时本地服务至租约到期再降级；Resize(0) 封禁排空。

**阶段二（本文主体）：严格预算协议，覆盖执行不可观测的第三方资源。**

§3–§9 的权威账本、Grant 状态机、Seal、隔离与恢复，以及 §12 的反例轨迹全部
属于阶段二。从阶段一迁移时替换预算后端；网关控制循环与本地准入结构不变。
§1 的威胁模型按阶段二口径撰写；阶段一按上述适用契约收窄解读。

## 1. 目标、威胁模型与不承诺的保证

目标按全系统 1000 万已准入在途 attempt、100 万准入 attempt/s 评估，允许多机多集群。
SDK 单实例承接其中一部分，须独立测其吞吐、尾延迟和内存；未声称单进程达到百万 QPS。
LLM 流式请求在可靠结束前占用额度，重试/对冲的每个上游 attempt 分别计数。
稳态 N≈λW，因此两项目标同时成立时平均持有约10s；收到请求QPS、准入QPS、
排队数、在途数及完成速率必须分开。1000万在途不等于1000万等待者。

第三方 API 不可控制：节点崩溃、网络超时、取消ctx或断开连接，不证明上游执行结束。
默认策略为安全优先：不把尚未安全回收的授权重新分配；允许故障后容量长期隔离。
没有可信结束证据或上游硬执行时间界时，不承诺有限时间自动回收，也不承诺长期满利用率。
账本守恒不是对第三方真实运行数的直接测量；后者还依赖正确集成和结束判定。

信任模型：网关/SDK正确遵循冻结与完成协议，不能在permit结束后再次发送、重复发送却只计一次、
或绕过SDK调用上游。控制面验证身份与配额，不能仅靠客户端自报NodeID允许重启绕过配额。
权威账本必须线性化、确认写不可在故障切换后丢失；读取旧副本、丢失已确认grant或双主分配
均不能作为安全实现。后端能否满足须另行验证，本文没有给普通Redis异步复制附加安全保证。

逐请求 Shared 的申请/释放在100万准入/s下已约200万远程调用/s，另有续租和等待轮询。
若另有1000万等待者每50ms轮询，其理论轮询需求约2亿/s，但这是压力反例，不是目标流量构成。
单资源串行修改和快照处理也会限制热点；不由此断言所有分片方案或精确公平在数学上不可能。
本方案将请求级仲裁留在内存，将远程仲裁提升为预算块；改善倍数须由活跃关系、chunk数及续约频率实测。

## 2. 三层结构与职责

```
策略控制器（慢循环：目标、SLA、隔离上限、停用策略）
                │ 版本化目标，不直接凭目标值释放占用
                ▼
预算分配器（按容量域分片的权威grant账本）
                │ 幂等授予 / 续约 / 归还 / 隔离 / 恢复
         ┌──────┴──────┐
       网关A          网关B …
       BudgetManager + 本地Airlock（请求级准入、公平、有界等待）
```

- 容量域按实际共享约束划分，例如provider/account/model-region；不是按终端用户建全局池。
- SLA可以使用独立保留池；第一版不自动跨SLA借用。硬隔离会牺牲空闲容量利用率。
- 逻辑tenant/API key用于本地公平，身份和用户配额由外层负责，不能认为本地轮转自动构成全局FIFO。
- 分配器Owner=(StableGatewayID, IncarnationID)，每次启动产生新incarnation，旧授权不自动继承。
- HeldCap按(容量域, StableGatewayID)跨incarnation计算，含Active/Draining/Quarantined，
  在授予提交点强制检查。StableGatewayID必须绑定可信部署身份，不能随意换ID绕过。
- Shared.Request.Tenant=网关ID可用于复用排队策略；MaxQueuedPerTenant只限制排队申请，
  不限制已经持有的额度，不能代替HeldCap。
- SDK不执行LLM任务；调用方负责实际发送、结束判定和业务重试。速率/计费/幂等业务属于外层，
  组合时避免长期占住并发额度等待其他配额。

## 3. 权威账本与不变量

每份chunk授权包含不可复用GrantID、容量域、Owner、Held、State、Revision、AdmissionUntil。
Held是尚未安全归还的加权并发额度；一次attempt默认weight=1。额度归还后可复用，不是QPS消耗令牌。
State为Active/Draining/Quarantined/Closed；AdmissionUntil只是新增准入期限，不是额度释放期限。

正常容量C未缩减时：Sum(Held of every non-Closed grant) <= C。
Quarantined完整计入；可分配量为max(0,C-Sum(Held))，还须满足每个网关HeldCap。
缩容只降低目标：允许已有Held暂时超过新C，此时停止新增授予并排空；不能把超出的部分立刻视作空闲。

多SLA池共享父容量时，池额度必须有父账本背书，不能对每池独立设置完整C。
第一版固定划分父容量，Sum(池分配额度)<=父C。动态跨池移动只在捐出方冻结并安全归还后授给接收方；
本地/Shared非抢占式Resize不能证明捐出方已排空。动态父子原子转移/借用不是现有原语附送的功能。

## 4. Chunk与记录规模

第一版以整块授予/归还降低部分释放协议复杂度。可实验面额q*2^k（k=0..K）。
单grant额度固定为实际面额b=q*2^k，成功Return将其Held从b变0并Closed；节点减少预算通过归还整块子集完成。
第一版不拆分grant；若只有部分占用得到排空证明，不能据此关闭整个chunk，部分归还另行设计。
只有目标处于可表示范围、面额齐全且各面额至多一块时，才有K+1块表示的上界；
实际增量申请可能产生重复块，必须单独限制MaxChunks并设计排空合并，不能任意声称“十张表示所有目标”。
最小量子q会产生舍入与碎片；大weight超过可获得预算或HeldCap时应拒绝，不无限排队。

存量不是“约几十条”：N_nonclosed=N_active+N_draining+N_quarantined。
前两项按实际(容量域,StableGatewayID,IncarnationID)持有关系乘平均chunk数估计，隔离单列且不重复计数。
正常固定C且最小块q时N_nonclosed<=floor(C/q)；此外还有已关闭恢复记录及控制操作幂等记录，
后者受操作速率、恢复/封印保留与安全压缩策略影响，不能假定只保留TTL那么久。
若复用现有Shared，MaxRecords还包含释放/拒绝等终态，不能只按当前持有块数规划。

## 5. 分配器状态机

| 当前状态 | 事件/条件 | 新状态与额度效果 |
| --- | --- | --- |
| 不存在 | 授予请求通过容量/HeldCap检查 | 原子创建Active并占用Held，随后才返回响应 |
| Active | 截止前、owner/revision匹配的续约 | Active，仅延长AdmissionUntil；不增加Held |
| Active | 主动排空/停用目标 | Draining，不释放Held |
| Active或Draining | 准入期限到期/失联处理 | Quarantined，剩余Held不变 |
| Active/Draining/Quarantined | 原进程安全归还已冻结空闲整块 | 该grant的Held原子从b变0并Closed |
| Quarantined | 原incarnation内存完整、控制操作对账完成，恢复获准 | Active或Draining，新revision/期限；Held不重复发放 |
| Quarantined | 可信恢复流程证明整个chunk无活动或不确定执行 | 回收整块并Closed；部分证据不得关闭整块 |
| Closed | 任何旧续约/恢复/重复消息 | 不复活；幂等返回或拒绝 |

授予响应丢失：账本已记账但SDK不得先用猜测额度；按原OperationID查询/重试，不能换ID再领一份。
续约响应丢失：不采用未确认的新期限；可继续使用原已知期限内的额度，到期后冻结新增。
普通迟到Renew不能把Quarantined变Active；必须走显式恢复。Closed永不复活，GrantID永不重用。

## 6. SDK状态、请求与不确定执行

SDK生命周期为Running/Draining/Frozen/Closed，控制RPC的pending/unknown独立记录。
Running仅在已确认期限和可用预算内新增；Draining/Frozen均停止新增，不能只禁止获取新chunk却继续消耗旧额度。
本地截止按单调时间、剩余时长和完整往返保守换算；旧revision响应不得复活更晚的冻结/关闭状态。

本地维护F(账本空闲)、I(已占用，包含已拿permit但未发送)、U(结果不确定)、P(已冻结待归还)。
稳定已对账时F+I+U+P等于尚未归还的Held；RPC在途时两边不要求瞬时等式，SDK采用保守可用下界。
P与U均不能自动放回F。F不自动代表可新增额度：逐chunk计算E，只汇总Active、
已确认且本地保守期限未到、没有待归还冻结的chunk。过期/Draining/Quarantined的空闲额度不计E。
第一版保守地将同owner同域全部I+U占用计入该池，新增重量w必须满足I+U+w<=E。
任一chunk失效或被撤出E时，先关整个本地池的门，在同一同步边界重算E与占用，
再以缩小的E恢复准入；I+U>E时保持停止新增直到排空或显式恢复，不遗忘旧I/U。
这会牺牲部分利用率，但不能让一个有效chunk替另一个过期chunk打开门。

请求路径：

```
检查授权/停用门 → 本地加权TryAcquire
  ├─ 可准入：立即计I（包括尚未发送）→ 调用方发送一次上游attempt
  │    ├─ 确认未发送或可靠完成：I减少，额度可本地复用（仍受E限制）
  │    └─ 超时/断流/结果不明：I转U，不自动释放给下一请求
  └─ 不可准入：有界等待或快速拒绝；取到permit后再次检查授权门
```

队列必须明确数量与等待时限，Resize暂停和预算失效时已有排队者也不能绕过授权门。
有效门检查、permit取得及计I必须对冻结/归还线性化；若先等到本地permit，须在同一同步边界内
复核门并计I，否则撤销这次未发送许可，不向调用方交付可执行授权。不能把检查门放锁外后直接放行。
SDK检查与真实网络发送之间仍可能暂停；已计I的permit继续占用账本，不能凭截止时间删除。
已完成/取消的permit不得再次用于发送；单个permit不能承载多个上游attempt。
第三方真实终止无法由SDK单独验证，Complete只是可信调用方的承诺；普通defer Release在不确定错误路径上不安全。
未来可提供Complete/MarkUncertain/ResolveUncertain式语义，但这些不是现有Permit新增能力。

## 7. 归还前冻结、排空与未知结果

归还面额b的chunk前，BudgetManager需在与本地申请互斥的边界内，降低准入目标并预留b，
预留b后重新计算E。必须I+U<=E，并在已对账账本上满足I+U+P_existing+b<=Held，
不能把已经待归还的额度再归还一次；额度只能在同owner、同容量域内合并计算。
必要时先停止新增，等待I下降。若U仍使剩余额度不足，则继续等待/隔离，不归还。

只有确认空闲的b才进入P并提交ReturnBudget。之后无论网络结果如何，都不能再本地使用这b。
分配器原子减少Held并释放给其他节点。响应丢失时保持P冻结，用原操作ID对账；
一次GetOperation返回NotFound不能解除冻结，因为原RPC可能仍在路上。
只有SealOperation原子确认未执行并持久封印旧操作，才允许取消冻结；封印结果也未知时继续冻结。
不能简单遇错、看到NotFound或客户端等过ApplyBefore就回滚本地capacity。
取消P后仍须重新检查当前状态、停用策略和逐块有效期，不能因此延长旧授权或自动打开门。

例如Held100、I90，不能Resize36后立即归还64；必须先让I+U<=36且没有其他未计入冻结，才可提交归还。
本地Resize允许已有占用超新容量，只能作为停止新增/排空工具，不是“已经排空”的证明。
整块归还需要冻结门与并发申请协调；不能在读Stats后、未锁住准入的情况下直接Release chunk。

## 8. 失联隔离、停用与恢复

- 网关崩溃/假死：到期转Quarantined，Held完整保留。心跳失联可提前报警或阻止续约，不能释放额度。
- 控制面不可达：新预算不可获；可使用最后确认的有效授权至本地保守截止，随后停止新增。
  已有I/U继续计账。可用宽限取决于故障时剩余有效期，可能接近0，不保证总能获得完整TTL宽限。
- 控制器不可达：分配器保留最后策略，但仍执行授权期限、隔离和HeldCap；不能自动放宽限制。
- 停用/封禁：分配器拒绝新授予和普通续约；已连接SDK立即关新增门并排空。
  失联SDK的新增停止保证只能依赖其最后已确认期限及正确集成；旧请求何时结束没有TTL上界。
  Resize(0)只阻止新grant，现有Shared租约仍可续约，不等于本协议的停用/撤销。

原进程恢复：保留完整I/U/P/控制操作状态，以原incarnation查询权威grant和操作结果；保持Frozen，
对账完成后显式Resume。若获准恢复，仅为原Held重新开放准入，不发第二份额度。
迟到的旧续约响应不能覆盖恢复后的revision或冻结状态。

重启恢复：生成新incarnation，不因同NodeID自动继承旧grant；旧Held仍计该网关HeldCap。
新进程可在剩余全局/网关配额内获新grant，旧授权保持隔离。仅有中心上次Stats快照不够，
因为报告之后可能已有新请求。第一版不引入逐请求本地WAL来承诺崩溃后重建执行事实。

隔离解除仅允许：原进程可靠对账并安全归还，或可信恢复方提供无剩余执行的依据。
恢复流程需要停止/排空旧执行者，防止其随后发送尚未发送的permit；新owner不能凭空声称旧执行已结束。
若未来具备上游入口拒绝过期授权和最长实际执行时间D，可另行证明T_cutoff+D+安全余量的回收界（T_cutoff为上游强制拒绝新增的截止时刻）；
客户端timeout、均值/p99耗时、普通epoch都不是该证明。本方案默认没有这些前提。
无可靠证据时隔离可以无限期，达到容量/隔离告警预算后明确降载拒绝，不无限补发“应急额度”。

## 9. 拟议控制API与幂等边界

以下是接口职责，不是新增Go接口或可调用API：

| API | 职责 |
| --- | --- |
| AcquireBudget | 幂等授予整块，校验容量域、网关HeldCap、最小/期望值、MaxChunks |
| RenewBudget | 续Active的新增准入期限，不增加Held，不自动复活隔离 |
| ReturnBudget | 原incarnation归还已经永久冻结的空闲块，不能用在途/不确定占用冒充空闲 |
| BeginDrain | 标记停止新增并排空，不回收占用 |
| GetBudget / GetOperation / ListOwnerBudgets | 权威对账，列表包括旧incarnation的隔离记录，访问受身份约束 |
| SealOperation | 与首次执行原子互斥；已执行则返回原结果，否则持久封印该操作并推进拒绝旧执行的栅栏 |
| ResumeBudget | 原进程在完整事实对账后显式恢复，停用策略优先，不绕过封禁 |
| ResolveQuarantine | 可信恢复方按证据回收，保留审计；不提供普通业务随手ForceRelease |

变更命令携带OperationID、不可变参数、Owner/GrantID、ExpectedRevision及ApplyBefore。
同ID同参数返回原结果，同ID不同参数冲突；成功重试不再次扣额或刷新原续约期限。
同grant的变更由SDK串行协调；版本冲突先对账。授予还需在StableGatewayID配额边界串行化。
ApplyBefore是首次执行的拒绝条件，不单独构成永久未执行证明。NotFound加时间经过也不能解冻：
领导权切换可能带来墙上时钟回退。SealOperation必须与原操作竞争同一个原子执行边界，
封印成功后任何迟到/重复副本都不能首次执行，即使时钟回退或主节点切换。
封印还需绑定Owner、操作内容及授权作用域；Acquisition尚无GrantID时也必须能在Owner/容量域内封印。
若原操作已执行，Seal返回该结果供对账，不撤销已发生授予/归还。
未证明安全压缩前不得定时遗忘Seal/Closed防重放记录；后续可用持久序号水位或持久单调时间栅栏压缩，
但须证明跨切换仍拒绝旧消息。不能仅依赖客户端本地单调时间或旧副本查询。客户端应用响应需检查状态与revision。

这些能力必须由权威账本实现，不能靠网关自报的目标值、Stats或租约数推导。
第一版以非拜占庭SDK协议为前提；ResolveQuarantine的执行事实由可信应用验证，分配器不能替第三方证明它。

## 10. 控制循环、公平与容量参数

实验循环可从3s采样、headroom1.3、低利用率连续两周期开始，但都需要实测。
需求使用加权占用I+U、最近峰值及有界队列的待申请重量，不能把queued请求个数直接与加权额度相加。
本地Stats只用于目标估计，不作为可回收或已完成证明。
不足时按HeldCap/剩余容量申请，未知授予先对账；过剩时执行第7节冻结排空，再整块归还。
捐赠两周期只能是健康空闲无U情况下的目标，不是对失联/长请求的回收保证。

硬最大份额意味着单网关再忙也不能拿完池，不能同时承诺完全work-conserving。
第一版明确选择硬HeldCap；只对未受上限约束、可安全分配的空闲额度讨论利用率。
分配器必须有独立的授予选择规则，HeldCap不是公平算法。第一版按StableGatewayID轮转有界的
待授予请求，同网关多个incarnation共享选择队列，重试不刷新排队位置；SLA隔离在上层池完成。
这保证选择机会的弱公平，不保证等权重额度或全局完成顺序。在稳定策略、有限竞争且请求持续满足
整块容量/HeldCap条件时，不能让该请求被无限绕过；具体队列、超时与空请求处理由原型定义并验证。
不承诺全局FIFO或“一个chunk*周期数”的时间公平界；
在不可抢占、长时占用或隔离存在时，任何固定收敛时限都需要额外前提。
若未来改软份额借用，需另定撤回与排空协议，不能直接降低capacity后把借出额度再用一次。

规模以活跃pair而非部署总数计算。续约调用量约为Sum(ActiveChunks/RenewInterval)，
另计授予/归还/恢复/策略流量；这是预算块级协调，不是每处理一块数量的请求就重新领预算。
例：1000节点、每节点1000准入/s、10000在途，合计100万准入/s与1000万在途；只是目标分解。
若每节点仅1活跃池、均10块、每5s续块，约2000次续约/s；20活跃池则约4万/s，
均不含重平衡、失败和存储成本。连接内存、实例数、Redis配置、持有量上限均待实测，不给未验证的机器规格。
排队与429仍先消耗入口资源，不能假定拒绝流量天然被LB/CDN吸收。

## 11. 与现有Airlock的差距和实现顺序

本地New、加权准入、FIFO/轮转、有界队列和Resize(0)可作为原型构件。
共享层现有五方法及driver可作对照或研究参考，但不能直接作为第三方严格预算账本：
现有Shared在TTL后回收容量；任意Renew错误会永久失效本地Lease，不支持本文“继续用已知旧期限”的预算语义。
当前Shared的Resize是非抢占式容量修改，不是租约撤销或排空确认。

因此撤回“必需改动为零”：必须新增预算权威状态、隔离计账、HeldCap、冻结/排空与恢复协议，
以及不确定attempt的调用方集成。是否扩展现有Driver或提供独立预算后端，留给原型API评审；
不为复用Transition强制相同存储/执行方式，也不在本提案加入通用ReleaseN或每请求持久化功能。

建议顺序：先按"阶段划分"交付阶段一（现有 Shared 上的预算块租约，适用契约
见 §0），独立评审后再做阶段二的纯确定性预算模型与最小原型，再测单机SDK与分片控制面，
最后做长时、开放环、跨节点故障实验。#61是逐请求Shared的独立性能工作，不能证明本方案已实现或具备生产容量。

## 12. 验收条件与反例轨迹（均是拟议测试，当前未实现）

确定性模型需分离分配器、SDK、网络和第三方执行者；假死/断网不会自动停止第三方任务。
检查每次事件的状态，不只检查最终计数；模拟延迟、乱序、重复、丢失响应、时钟边界与重启。

| 轨迹 | 必须成立的结果 |
| --- | --- |
| 授予提交后响应丢失，随后重试 | 同OperationID只创建一个grant，未知期间SDK不先花额度 |
| Active续约提交/响应丢失，到达旧本地截止 | 未确认新期限不得延长本地新增；过期冻结；服务端Held不释放 |
| A发出请求后崩溃，超过TTL；第三方仍运行；B申请 | A隔离计账，B不得获得A尚未安全回收的额度 |
| SDK检查有效后暂停，授权过期后恢复发送 | 已占用permit仍计I/隔离预算；不得凭过期或新进程重用而提前回收 |
| Held100/I90尝试归还64 | 不得立即归还；先停新增，只有剩余预算能覆盖I+U时才提交 |
| 冻结b与本地Acquire并发 | b不可能同时成为待归还和新请求可用额度 |
| Return已提交但响应丢失，空闲被授给B | A保持b冻结，同操作重试不重复归还，迟到响应不恢复本地b |
| Return未执行但仍在网络中；查询NotFound | 不解除冻结；须由SealOperation持久封印未执行操作，或确认已执行结果 |
| NotFound后时钟回退/leader切换，迟到Return抵达 | 时间不构成否定证明；Seal未执行确认后旧Return永不可执行，原来已执行则返回原结果 |
| 64额度chunk过期、36额度chunk仍有效，64仍空闲 | 关门重算E=36，不能继续按100准入；旧I/U也保守保留 |
| timeout/断流后未知请求 | 转U不自动复用，不能以平均时长或客户端deadline清掉U |
| 同进程保留I/U/P恢复；重启丢失这些事实 | 前者对账后可显式恢复；后者新incarnation，旧Held仍隔离且计HeldCap |
| 旧Renew/Resume/Return乱序或同ID不同参数 | 版本/身份冲突，Closed不复活，不重复增减额度 |
| 停用时仍有有效grant、旧客户端失联 | 拒绝新授予/续约/恢复，已连SDK关门；旧占用没有TTL内排空保证 |
| 退还/换池时持有仍超新目标 | 未排空部分不转移到新池；父域账本不得双计可用 |
| 网关更换incarnation反复申请，或固定50%上限而其余闲置 | 前者不可绕过HeldCap；后者允许利用率受限，不伪称work-conserving |
| 三网关持续竞争、其中一个一直可满足却被选择器绕过 | 违反弱公平验收；固定HeldCap本身不足以使该轨迹合法 |
| Complete/MarkUncertain/Resolve重复或并发，或旧permit再次使用 | attempt只结束一次，I/U不能重复返还，结束后禁止再发送 |
| 存储领导权切换/复制回退丢失确认授权 | 必须拒绝该后端安全验收，不能用SDK模型掩盖重复分配 |

模型安全性质：固定C时Held总和不超C（缩容例外不新增）、归还不重复、U/隔离不因时间自动释放、
本地新准入受有效授权和可用额度共同约束。第三方在途计数模型只能在可信发送/结束假设下验证，
不能据此证明任意外部API绝不超并发或租约到期可终止真实计算。

健康场景活性：在第10节的稳定策略、有限竞争及请求持续可满足整块条件下，且有可分配容量、
HeldCap允许、控制面可达、无U阻塞及请求能完成时，
持续需求最终获预算，空闲块经过冻结可归还；具体时间界由参数与模型推导，不预设两周期/TTL必达。
负载验收采用固定到达轨迹、多种子、真实持有时长分布及开放环；分别统计收入/准入/完成QPS、
在途、队列、拒绝、控制操作、Held利用率、隔离量、碎片、p95/p99、CPU与内存。
不以毫秒延迟作为CI硬门槛；内存模型不证明网络故障、后端持久性或生产吞吐。
