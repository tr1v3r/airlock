# RFC 001：按租户公平的有界并发准入

状态：单令牌实现已落地于当前开发分支，尚未发布版本。

公开入口为 `New(Config)`，`Stats()` 返回 `Stats`。实现从内部原型迁入根包，
`internal/fairgate` 已移除；比较测试直接调用公开 API。公开 Pool 已移除，channel 策略仅作测试基线。
原型实测见[历史实验结果](001-experiment-results.md)，不代表本实现已通过生产性能验收。

## 决策摘要

为 Airlock 增加独立的 `Airlock`：在一个进程内，按租户轮转分配单个并发名额，并限制全局及单租户等待人数。公开 Pool 被移除，单令牌语义保持不变。

首版重点是可解释的排队隔离和共享容量，不是重写一个更快的 semaphore。一次申请多个令牌、租户份额、自适应容量均不在首版范围。先验证单权重情况下的价值，再设计权重与公平性的组合。

## 场景与证据

假设共享下游允许 20 个并发请求。租户 A 提交大量批处理，租户 B 偶尔提交交互请求。全局 FIFO 能保证容量，却不能避免 B 排在 A 的积压之后；固定租户上限能隔离，但单租户独占时可能浪费全局容量。

拟解决：等待中的租户获得轮流进入的机会，单租户不能用无限队列挤占等待空间；仅一个租户活跃时允许它使用全部执行容量。

外部需求依据，不代表 Airlock 已获得使用验证：

- [Go #56910](https://github.com/golang/go/issues/56910)：真实系统受队首大请求阻塞影响，使用者最终拆分大小请求 semaphore；也有使用者依赖 FIFO。
- [Kubernetes APF](https://kubernetes.io/docs/concepts/cluster-administration/flow-control/)：总并发限制之上增加流量隔离、有界排队与公平调度。
- [Netflix concurrency-limits](https://github.com/Netflix/concurrency-limits)：按流量组保护共享容量。
- [Failsafe-go prioritization](https://failsafe-go.dev/execution-prioritization/)：已有按优先级、用户使用量做过载拒绝的方案；需作为实际接入阶段的替代方案评估，不能宣称生态空白。

## 当前 API

以下为接口摘要：

```go
type Config struct {
    Capacity           int
    MaxQueued          int
    MaxQueuedPerTenant int
}

func New(Config) (*Airlock, error)
func (*Airlock) Acquire(ctx context.Context, tenant string) (*Permit, error)
func (*Airlock) Stats() Stats
func (*Permit) Release() // 并发安全，重复调用不重复释放

type Stats struct {
    Capacity       int
    InUse          int
    Queued         int
    WaitingTenants int
}
```

使用方式：`permit, err := gate.Acquire(ctx, tenantID)`，成功后立即 `defer permit.Release()`，任务仍由调用方执行。

配置规则：`Capacity > 0`，两个队列上限均非负，`MaxQueuedPerTenant <= MaxQueued`；非法配置构造时返回错误。零队列上限表示不能等待，而不是无限排队。第一版不提供无限模式。

`tenant` 必须非空；相等字符串视为同一租户。身份由可信业务代码提供；伪造大量不同租户可破坏公平性，本库不负责身份认证。传入 nil context 属于调用错误，panic。字符串字节数和调用方 goroutine 内存不由队列条数上限严格约束，调用方应限制身份长度及上游请求数。

错误契约：无效租户返回 `ErrInvalidTenant`；排队人数超限返回 `ErrQueueFull` 或 `ErrTenantQueueFull`；取消返回 `ctx.Err()`。顺序：参数校验、取消检查、尝试准入、检查全局队列上限、检查租户队列上限。两个上限同时触发时优先返回全局错误。

## 调度契约

1. 所有申请权重固定为 1；每次授予在同一临界区完成容量计数和请求状态变更，不存在部分获取。
2. 有空位且无等待者时立即准入。已有等待者时，新请求不能抢占等待者的调度机会。
3. 每个租户有 FIFO 等待队列；非空租户队列组成一个轮转列表。新活跃租户加入列表尾部。
4. 每次取列表头租户的一个请求。若该租户仍有等待者，移到尾部；否则移出列表。有多个空位时重复执行。
5. 等待队列上限只统计尚未授予名额的请求。先处理已有可调度请求，再决定新请求是否需要排队以及队列是否已满。
6. 当可用容量为正且有等待请求时，持续派发直到容量耗尽或队列为空。没有固定每租户执行上限；允许唯一活跃租户使用全部容量。
7. 仅保证等待租户之间的放行轮转，不保证 CPU、公平运行时长、吞吐比例或尾延迟。对于持续非空的固定租户集合，每轮各放行一个；后到租户插入尾部，不越过已经排队的租户位置。
8. 已运行请求不被抢占。新租户可能等待已有长任务释放容量；没有任务时长上限，就没有绝对等待时限保证。

公平契约只覆盖已进入等待队列的请求。全局队列满时，新租户也会被拒绝，首版不做队列空间预留或驱逐；若希望单租户不能独自占满全局队列，应配置 `MaxQueuedPerTenant < MaxQueued`，但多个繁忙租户仍可共同填满队列。

示例：容量已占满，等待顺序为 `A1 A2 A3 B1 B2 C1`。等待租户顺序为 `A B C`，逐次释放一个名额后，放行顺序应为 `A1 B1 C1 A2 B2 A3`。

## 取消、释放与状态回收

状态机：`waiting -> granted` 或 `waiting -> cancelled`；授予和取消在同一把锁内串行化。

- 已取消 context 不准入。排队后取消若先取得状态变更权，移除请求，不占容量，并继续调度。
- 授予若先完成，允许成功，即使 context 随后取消；返回成功则必须释放。返回错误则绝不残留名额。
- Permit 仅由库创建，记录授予者，释放一次；并发或重复 Release 是 no-op。禁止值复制，文档明确只使用指针；nil/零值 Permit 释放无操作。不会用 finalizer 或计时器自动回收。
- 租户队列为空时立即移除队列索引。已授予 Permit 只需持有 Airlock，无需保留租户索引；首次实现不维护每租户历史指标。
- `Stats` 是同一锁内的一致快照，不是批次完成屏障。必须满足 `0 <= InUse <= Capacity`、`0 <= Queued <= MaxQueued`、`WaitingTenants <= Queued`。
- Airlock 不执行任务、不创建内部 worker、不收集结果或任务错误；无需后台维护 goroutine。

## 内部实现候选

一把互斥锁保护容量、等待计数、租户 map、租户轮转双向链表和各租户等待双向链表。等待请求持有通知 channel 与链表节点指针，便于取消时 O(1) 移除；释放后在锁内预留名额，再通知获得者。

通知 channel 用于唤醒，不用于容量计数。运行时仅用标准库。加锁版和基于 Weighted 的调度封装都允许作为原型，依据契约清晰度与基准结果选择；不以原创底层算法为目标。

## 明确不做

首版不实现多权重、租户权重/优先级、动态容量、执行超时强制回收、分布式配额、任意策略插件、HTTP middleware、Prometheus 依赖、Close/Drain 或 worker 生命周期。后续权重设计需单独解决队首阻塞和饥饿，不能直接循环 Acquire。

## 比较对象与现有实验

`internal/comparison` 为测试专用包，`golang.org/x/sync v0.16.0` 仅作测试依赖（兼容本仓库 Go 1.24，不声称它是最新版）。测试依赖不进入运行时；channel 基线只存在于比较测试中。

当前分两层证据：

1. 确定性策略模型：全局 FIFO、固定每租户额度的两级模型、按租户轮转模型。使用真实 Weighted 的 TryAcquire/Release 记账，但排队由测试模型维护，不代表 Weighted 内部队列的真实并发执行轨迹。
2. 真实调用测试：Weighted.Acquire 的取消与容量恢复，以及 tenant-first 两级 Acquire 的取消回滚和取消/释放竞争。后者没有证明轮转实现的并发正确性。

两级模型有意给出有利条件：跳过被租户额度阻塞的请求、不持有无用的全局名额。这比简单的嵌套阻塞调用更强，避免只挑明显错误的比较对象。

| 实验 | 输入 | 预期/验证指标 |
| --- | --- | --- |
| 洪峰后稀疏请求 | 容量 1，等待 32 个 A 后到达 B | FIFO/两级模型 B 第 33 个；轮转 B 第 2 个 |
| 单租户利用率 | 总容量 8，A 有 16 请求；两级租户上限 2 | FIFO/轮转占用 8，固定上限模型占用 2 |
| 两级额度正面案例 | 总容量 4，租户上限 2，A 积压后 B 到达 | A 占 2 后 B 可获得名额，证明基线确实有隔离能力 |
| 多租户与取消 | A/B/C 各两个请求，取消 C | 按 A/B 轮转，C 不留活跃队列记录 |
| 队列限额 | 全局 3，每租户 2 | A 第三个拒绝，B 可入队；取消后恢复队列空间 |
| 真实取消与竞争 | 单级及 tenant-first 组合 | 错误不泄漏名额，成功后释放恢复全部容量 |

这些结果只验证模型和比较适配器，不能证明产品已实现或真实负载更快。尤其不能由放行名次推导具体 p99；固定额度模型的低利用率也是配置取舍，并非两级方案总是低效。

2026-10-22 本地验证：上述全部比较测试通过，观测到 B 放行名次分别为 33/33/2，单租户占用分别为 8/2/8。全仓 `go test ./...`、`go test -race ./...` 与 `go vet ./...` 通过。没有运行生产负载测试，尚无 p99、吞吐回退或内存长期稳定性的测量结果。

运行：

```sh
GOWORK=off go test -v ./internal/comparison
GOWORK=off go test ./...
GOWORK=off go test -race ./...
GOWORK=off go vet ./...
```

## 验证状态与后续计划

阶段 1：根据单令牌实现授权，公开 Config/New/Stats/Permit 和错误值，移除 Pool。

阶段 2：公开实现已覆盖以下黑盒并发测试：公平顺序、快速路径不插队、取消与授予竞争、Permit 重复释放、瞬时多空位派发、零队列模式、短命租户回收。使用同步屏障，时间只作测试超时保护；运行 race。

阶段 3：真实负载对比，增加原始 Pool、单 Weighted、tenant-first 两级组合（租户上限扫描 1/容量一半/容量）、Airlock。固定到达轨迹和服务时间分布，多随机种子，记录每租户排队 p50/p95/p99、完成率、拒绝率、总吞吐、allocs 和内存；拒绝与取消必须计入，不能只统计幸存请求。

运行两个独立比较：不触发队满时隔离调度收益；相同等待预算时比较过载行为。两级适配器如补充队列预算须单独标注。增加长短任务混合，揭示轮转在非抢占条件下的局限。

建议实验门槛（目标，不是实测）：单租户稳定负载吞吐相对单 Weighted 回退不超过 10%；同服务时间的 A 洪峰/B 稀疏场景，B 排队 p99 至少改善 50%，且不得靠增加 B 拒绝率达成。报告完整配置及多次分布；若不满足，优先修正假设而不是调测试迎合结果。

阶段 4：至少一个真实多租户调用场景接入评估，并与 Failsafe-go 的现有策略比较接入成本。当前没有接入方承诺。

停止条件：需求只是总并发控制；现成工具已能低成本满足；公平收益只存在于刻意案例；或维护/性能成本超过隔离收益。满足停止条件则保留实验和结论，不发布新增 API。
