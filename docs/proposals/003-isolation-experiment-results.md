# 高组容量隔离实验结果

状态：独立 PR 中的方案验证，未新增公共 API、未合入 dev 或发布。本报告衡量 Airlock 准入，不是业务执行 SLA。
实验基于当前本地优先级快照，具体契约见[方案](003-high-priority-isolation.md)。

## 结论与 API 决定

固定分区消除了本次负载中低组对高组令牌容量及受保护队首的影响：低组大请求和长持有场景，
共享池高组超时分别为 71/192（约 37%）和 94/192（约 49%），分区池均为 0/192。
低组初始小请求突发场景中，两种模式都接纳了全部高组请求，分区进一步减少了等待。

收益有明确代价。高组自身突发时，共享池成功 63/480，分区池只有 19/480；固定高组容量为 4，
不能利用低组的空位。只有低组负载时，共享池吞吐约 2136/s，分区池约 1482/s，下降约 31%。
不能用分区池更低的成功样本等待时间，掩盖它更高的失败比例。

**当前建议使用两个实例组合，不新增统一分区 API。** 本实验未要求修改核心调度器，就能实现
容量预算划分、独立队列、独立队首保护及等待期限。新增 API 不能扩大这一保证；可信路由和
容量选择仍需业务判断。只有后续多个使用方反复需要总预算校验、统一统计、配置迁移时，
再设计封装。不把容量借用、抢占、任务重试或在线迁池附带加入。

## 实验设置

- Darwin arm64，Go 1.24.13，GOMAXPROCS=12；未固定 CPU 核或系统背景负载。正式数据采集
  未同时运行本任务的 lint/race 检查；race 验证另跑，其时延不混入本报告。
- shared：单实例容量 12，H/M/L 选择份额 8:3:1；split：高组独立容量 4，中低组容量 8，
  中低组 3:1。实际生成 H/L 请求，M 为空。未增加外层全局门控，不借用、不溢出路由。
- 高组等待额度 16，低组 128，M 为 0，两种适配器额度相同；各组各两个租户。
  高组每次权重 1，低组权重最大 8，在两个模式下都合法，不用不合法大请求制造差异。
- 每个场景使用种子 1、2、3；对于同一 seed，两种适配器复用相同的计划到达、权重、持有时长
  和等待预算轨迹。适配器执行顺序随种子交替。计划相同不意味着 goroutine 实际入队顺序相同，
  尤其是同时到达的低组。
- 所有低组请求在 t=0 突发到达，形成有限积压；这不是无限持续到达流。高组从 t=10ms 开始。
  除 high-overload 外，高组每 1ms 一个，共 64 个，持有 1–2ms；等待预算均为 5ms。
- 预算从计划到达时刻开始，超时不重试。成功后按持有时长完成模拟任务再释放，即使等待
  context 此时已经超时。任务只 Sleep，不消耗模拟之外的 CPU/数据库资源，也不测执行取消速度。
- 外层 10s 仅为测试看门狗，触发会让测试失败。低组没有独立等待期限，全部必须成功。

| 场景 | 低组 | 高组 |
| --- | --- | --- |
| low-flood | 96 个，权重 1，持有 4–6ms | 64 个，间隔 1ms，持有 1–2ms |
| low-large | 32 个，权重 8，持有 8–12ms | 同上 |
| low-long | 32 个，权重 1，持有 40–60ms | 同上 |
| high-overload | 16 个，权重 1，持有 4–6ms | 160 个，间隔 50μs，持有 8–12ms |
| low-only | 96 个，权重 1，持有 4–6ms | 无 |

## 高组等待与失败

下表成功/排队拒绝/超时为三个种子的合计；分位数是每个种子分位数的算术均值，
不是将全部样本合并后的分位数。时间单位 ms，保留三位小数；0.001 只是约 1μs 的
无竞争调用测量，不能解释为生产延迟保证。分位数按排序后 `floor((N-1)*p/100)` 取值；
成功样本少时 p99 代表性尤其有限。原始数据还保留每次最大成功等待时间。

成功等待与全体返回时间从**实际调用 Acquire**开始到返回，不包含启动延迟，也不包含任务执行。
启动延迟是计划到达到实际调用的时间；两列分位数不能直接相加推导端到端 p99。
全体返回样本包含成功、排队拒绝和超时，快速拒绝不能算作成功准入。

| 场景 | 模式 | 成功/总数 | 队列拒绝 | 超时 | 成功 p95 | 成功 p99 | 全体返回 p99 | 启动延迟 p99 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| low-flood | shared | 192/192 | 0 | 0 | 0.855 | 1.130 | 1.130 | 0.167 |
| low-flood | split | 192/192 | 0 | 0 | 0.001 | 0.001 | 0.001 | 0.168 |
| low-large | shared | 121/192 | 0 | 71 | 4.100 | 4.566 | 5.106 | 0.224 |
| low-large | split | 192/192 | 0 | 0 | 0.001 | 0.001 | 0.001 | 0.534 |
| low-long | shared | 98/192 | 0 | 94 | 4.014 | 4.224 | 5.063 | 0.273 |
| low-long | split | 192/192 | 0 | 0 | 0.001 | 0.001 | 0.001 | 0.239 |
| high-overload | shared | 63/480 | 348 | 69 | 4.745 | 4.761 | 5.007 | 0.034 |
| high-overload | split | 19/480 | 372 | 89 | 4.397 | 4.397 | 5.009 | 0.032 |

所有低组请求均成功、无拒绝或超时。本次高组没有“实际开始调用前预算已过期”的样本，
但出现了 6 次超过计划 deadline 才返回成功的情况：low-large/shared 2 次、
high-overload/shared 2 次、high-overload/split 2 次。这与“授予已完成优先于取消”的契约相容，
也可能包含返回调度延迟；公共 API 无法定位内部授予时刻，不能声称每次成功都在 5ms 内。
高组全部拒绝、超时和迟到成功均保留在原始记录中，没有过滤。

## 吞吐和保留容量代价

吞吐为成功请求数 / 从计划 t=0 到最后一个任务释放完成的时长，包含高低两类；
不同请求权重和持有时长不同，不能将不同场景的 requests/s 当作同等业务产出。
高组失败改变成功工作量，因此隔离模式吞吐变化不表示底层调度算法执行更快。

利用率是“调用方看到成功返回后、开始 Release 前”的令牌时间 / (12 × 实验时长)，
不包括内部已授予但尚未返回等不可见区间。它是令牌占用代理，不是 CPU/数据库利用率。
保留容量空闲率使用高组 4 个令牌与整个实验窗口作为分母，含高组尚未到达和已经结束后的时间；
不是仅在高组有需求时的空闲率。高组空闲资源不会借给低组。

| 场景 | 模式 | 总吞吐 /s | 总利用率代理 | 低组成功等待 p99 /ms | 高组保留容量空闲率 |
| --- | --- | ---: | ---: | ---: | ---: |
| low-flood | shared | 2143.2 | 65.4% | 41.895 | 不适用 |
| low-flood | split | 2143.7 | 65.4% | 57.490 | 67.5% |
| low-large | shared | 208.1 | 68.0% | 325.511 | 不适用 |
| low-large | split | 275.7 | 68.8% | 326.000 | 93.1% |
| low-long | shared | 398.6 | 85.6% | 104.126 | 不适用 |
| low-long | split | 430.6 | 64.1% | 160.347 | 89.3% |
| high-overload | shared | 1131.0 | 74.9% | 4.442 | 不适用 |
| high-overload | split | 698.7 | 38.7% | 6.095 | 48.4% |
| low-only | shared | 2136.1 | 91.3% | 38.029 | 不适用 |
| low-only | split | 1482.4 | 63.5% | 58.235 | 100.0% |

low-flood 的总吞吐接近，因为本轮任务结束时间由后到的高组完成时刻主导，不能据此认为
分区没有成本：低组等待 p99 已从约 42ms 上升到约 57ms。low-only 才直接展示高组保留容量
完全空闲时的损失。low-long 分区池的低组等待和整体排空时间也更长。

## 正确性验证与局限

确定性测试验证共享池中占用 7、剩余 5 时，已选择的低组 8 令牌请求会阻挡高组；
相同低组状态位于独立低池时，高组可以成功申请。还覆盖高组自身排满、等待取消后不重新
入队、申请 context 取消不撤销已授予 Permit、重复释放、容量总和和禁止跨池借用。
测试用状态屏障确定排队状态，不用延迟门槛判定正确性。

完整 go test、vet、lint、全部示例、模块检查通过；全套 race 与真实负载 race 通过，
核心运行时代码覆盖率 100%。本次新增测试、示例和文档，没有修改基线核心运行时代码。

这些是有限合成负载，三个 seed 不是统计置信区间。未测 CPU 竞争、数据库连接池、下游延迟、
真实任务取消、无限到达流或恶意租户。固定分区能阻断本库内的低组容量依赖，但高组自身过载、
调度暂停及外部共享瓶颈仍可能造成超时。下一阶段应在真实业务负载下，根据成功率和延迟一起
选择高组容量、最大权重、等待预算与队列上限；本报告中的 4/8、16、5ms 均不是通用推荐值。
