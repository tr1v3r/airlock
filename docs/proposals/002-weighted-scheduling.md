## 1. 推荐决定

第一版采用**原子多令牌申请 + 优先级组加权循环 + 组内租户轮转 + 租户内 FIFO**。某个请求一旦轮到，容量不足就保护该请求，停止后续授予直到容量足够或请求取消。容量共享，不预切固定令牌池；各优先级组独立保留等待队列额度。

这里的“高优先”是更多准入机会，例如高、中、低为 `8:3:1`；并非高组非空就永远不运行低组。持续高负载下，严格优先与低组不饿死不能同时保证。第一版选择可证明的最低进展机会，接受队首阻塞带来的吞吐损失。

公平按**请求选择机会**理解；各组持续积压且没有已选请求取消时，完整周期的成功授予比例才等于配置份额，存在取消时不保证成功授予比例。它不按令牌数、运行时间或 `令牌数 × 持有时间` 计量。请求权重只决定同时占用的容量。不同权重/持有时间下，不承诺各组资源占比为 `8:3:1`；若业务要的是资源份额，应另行定义成本计量后再设计，不把本方案包装为资源公平。

## 2. API 与配置

保留现有四个阻塞入口，避免变参和重载含义：

```go
func (a *Airlock) Acquire(ctx context.Context) (*Permit, error)
func (a *Airlock) AcquireFor(ctx context.Context, tenantID string) (*Permit, error)
func (a *Airlock) AcquireN(ctx context.Context, n int) (*Permit, error)
func (a *Airlock) AcquireNFor(ctx context.Context, tenantID string, n int) (*Permit, error)
```

`TryAcquire` 系列入口也保留原签名，不接受 context、不排队；有任何等待者或容量不足时返回 `ErrWouldBlock`，不能跨组插队。

`Acquire` 等价于默认租户的 `AcquireN(ctx, 1)`；`AcquireFor` 等价于 `AcquireNFor(ctx, tenantID, 1)`。默认租户仍是内部保留身份，与所有显式租户不同；显式空 ID 仍错误。

当前本地配置如下：

```go
type PriorityGroup struct {
    Name      string
    Turns     int // 一个调度周期中的请求选择次数，不是令牌权重
    MaxQueued int // 此组的独占等待请求额度
}

type PriorityPolicy struct {
    Groups       []PriorityGroup // 高优先到低优先，构建固定轮转表
    DefaultGroup string          // 默认租户与未映射租户的组
    TenantGroups map[string]string
}

// Config 新增 Priority *PriorityPolicy；其余字段保留。
```

优先级由构造 Airlock 的可信服务端配置决定，不提供 `Acquire(..., priority)` 让请求方自行提权。构造时深拷贝并验证配置；生命周期内不支持迁组或改份额。上层先认证，再把可信租户 ID 传入。库不认证用户，也无法阻止上层伪造大量租户 ID。固定映射的规模和更新需求可在后续 PR 单独处理，第一版不在持锁路径调用用户回调。

- `Priority == nil`：只有一个隐式组，继续现有跨租户轮转，不增加优先级配置负担。
- 启用时组名非空且唯一，每组 `Turns > 0` 且按组顺序不递增，总 `Turns <= 1024`，按给定顺序展开轮转表；防止配置导致无界内存/扫描成本。
- `DefaultGroup`、所有映射目标必须存在；`TenantGroups` 不接受空租户键。
- 各组 `MaxQueued >= 0`，安全累加且总和 `<= Config.MaxQueued`。如果要求低组过载时也能进入队列，必须为其配置正值。
- 各组队列额度不互借；全局未分配额度不自动变成共享额度。这样高组不能占掉低组的等待入口，代价是可能提前拒绝高组请求。
- `MaxQueuedPerTenant` 继续限制等待请求数，不限制持有令牌数。一个租户仍可在无竞争时使用全部令牌。

使用示意：

```go
p, err := a.AcquireNFor(ctx, authenticatedTenantID, 3)
if err != nil {
    return err
}
defer p.Release() // 一次归还全部 3 个；不让调用方再传释放数量
// 由调用方执行工作；Airlock 不启动 worker。
```

## 3. 权重、错误与计数契约

`Capacity` 表示令牌总容量 `C`。合法请求为 `1 <= n <= C`：`n <= 0` 返回 `ErrInvalidWeight`；`n > C` 返回 `ErrWeightExceedsCapacity`，立即失败、不入队。不会部分获取，也不会先占一部分再等剩余部分。

固定处理顺序：nil context panic → 显式租户 ID 校验 → 权重校验 → 持锁检查 `ctx.Err()` → 即时授予条件 → 全局队列上限 → 组队列上限 → 租户队列上限。新增组上限错误 `ErrGroupQueueFull`；已有入口在未启用优先级时保留原错误顺序。

即时授予仅允许**全局没有等待者且没有受保护请求**，并且 `n <= C - used`。即时授予不消耗组槽位或租户轮转机会。有等待者时新请求不能绕过调度器。队列上限只计算 pending 请求；可以即时授予的请求不受队列上限阻止。进入等待队列后，即使同次调度最终授予，也先通过队列额度检查，避免“刚好能执行”的隐式插队路径。

维护以下不变量：

| 状态 | 不变量 |
| --- | --- |
| 令牌 | `0 <= used <= C`；`used` 等于全部已授予、尚未释放 Permit 的权重之和 |
| 原子性 | 一个请求只处于 pending、granted、cancelled 之一；错误结果不持有令牌 |
| 排队 | 全局/组/租户计数与链表完全一致；受保护请求仍计入队列 |
| Permit | 成功一次获得一个 Permit；Permit 记住 `n`，Release 仅归还一次 |
| 公平索引 | 每个非空租户只在所属组轮转表出现一次；空租户及时回收 |

容量判断使用 `n <= C - used`，避免 `used + n` 溢出。构造期组额度/份额求和也要检查溢出。默认不增加容易溢出的排队权重总和统计。

`Stats.InUse` 改为持有令牌数；增加 `ActivePermits` 表示未释放凭证数。`Capacity` 是令牌，`Queued` 是请求，`WaitingTenants` 是租户，不能混用单位。原来的单令牌使用中 `InUse == ActivePermits`。本阶段不增加公开按组统计。后续可另提供快照，以组名为有限维度，避免默认输出无限租户标签。

## 4. 精确调度规则

以 `H:8, M:3, L:1` 为例，轮转表是 `[H,H,H,H,H,H,H,H,M,M,M,L]`。维护一个跨 dispatch 调用保留的游标，各组另有非空租户链表，租户有 FIFO 请求链表；另有至多一个 `protected` 请求。

在 Acquire 入队、Release、pending 请求取消后，在同一互斥锁下运行 dispatch：

1. 若 `used == C` 或队列为空，结束。不在容量完全占满时预选请求。
2. 若已有 `protected`，继续处理它，不能改选新到达的高优先请求。
3. 否则从游标扫描轮转表，跳过空组；至多扫描一圈。选中非空组后，取该组轮转表首个租户的队首请求，作为 `protected`。游标移到所选槽位之后；该租户若还有后续请求，在本次选择中消耗其一个轮转机会。
4. 若 `protected.n > C - used`，保持它及其队列节点，立即结束。后面的请求即使更小、优先级更高也不能插入；剩余容量暂时闲置。
5. 容量足够时原子执行：移出队列、增加 `used` 与 `ActivePermits`、标记 granted、清空 `protected`、关闭通知 channel，然后继续循环。

步骤 3 的租户轮转应实现为明确的内部状态：选择时将租户移到尾部（仅一个请求时仍保留到请求移除），之后授予或取消时不重复轮转；空队列立即移除。等待期间不能因新租户加入而改变已选请求。新租户加入所属组尾部。

取消一个已选请求时，该槽位和租户轮转机会**已经消耗**；移除请求、清空保护并重新 dispatch，不倒退游标。取消未选请求不消耗调度机会；参数/队列拒绝不改变游标和租户顺序。取消导致租户变空时正常移除。槽位跳过、选择、取消必须有确定性测试，否则不同 driver 很容易实现出不同公平性。

因此 `8:3:1` 精确适用于各组持续非空、没有已选请求取消的完整周期。存在取消时，份额是请求**选择机会**，不保证成功授予比例；空组的槽位直接跳过、不累计信用，不让空闲后恢复的组追讨历史份额。优先级模式关闭、请求全为单令牌时，不会出现容量不足的已选请求，保留现有租户 RR 行为。

### 容量不足的例子

`C=5`，当前持有 4 个令牌，轮到低组请求 `L(n=4)`，高组随后持续到达 `H(n=1)`：

| 事件 | used / free | 动作 |
| --- | --- | --- |
| 选择 L | 4 / 1 | 保护 L；H 暂不授予 |
| 旧 Permit 释放 2 个 | 2 / 3 | L 仍等待，空闲 3 个不借给 H |
| 旧 Permit 再释放 1 个 | 1 / 4 | 原子授予 L，变为 5 / 0 |
| L 释放 4 个 | 1 / 4 | 按保存的游标继续调度 |

这刻意避免“小请求永远填补释放空间，导致大请求永远凑不够容量”。代价是全局队首阻塞（HOL）：低优先的大请求可以延迟高优先的小请求。如果业务不能接受这种延迟隔离，应评估按组预留令牌/独立 limiter；不能一面允许无限绕过，一面继续声称大请求不饿死。

## 5. 不饿死保证的边界

保证对象是**已经被接纳到等待队列且持续未取消的请求**。必要前提：`n <= C`；已获 Permit 最终释放；调度与调用 goroutine 最终获得执行机会；队列有限，组份额为正；进程未崩溃。Airlock 不终止工作，也不回收忘记 Release 的本地 Permit。

证明思路：一个受保护请求阻止新授予；既有持有者最终释放，因此它最终有足够令牌。正份额的有限循环确保每个持续非空组最终被选择；组内 RR 使已有租户前面的租户不会永久重新插到它前面；租户 FIFO 使同租户后来的请求不能越过目标请求。对目标前面有限个请求归纳，目标最终被授予。

`8:3:1` 的低组持续非空时，两次低组选择之间最多有 11 次其他组选择；这不是某个低组租户的 11 次上界，也不是毫秒等待上界。低组多个租户继续按 RR 分摊，队列中的前序请求和每个 Permit 的持有时间会增加等待。无统一释放时限就没有固定等待时限；`context` 超时只是允许放弃，不能变成完成 SLA。

独占组队列额度防止其他组把低组的全部等待入口占满，但不能承诺每个新请求都能入队；低组自己也可能满，同组租户也可能占满组额度。第一版不做所有潜在租户的入口保障，不保证恶意无限新租户身份下的公平。

## 6. 取消、通知、释放

继续当前“锁内状态转换先发生者获胜”的契约，不复制其他库的不同取消偏好：

- pending → cancelled：取消先拿锁并移除节点，返回 `ctx.Err()`，不消耗令牌；若是 protected，解除保护并唤醒下一候选。
- pending → granted：调度先在锁内保留全部 `n`，之后即便 context 取消，也返回成功 Permit，调用方必须释放。
- 关闭 ready 只负责通知，不是容量事实来源；granted 标记和计数都先在锁内更新。
- Release 用 `sync.Once` 同时支持并发和重复调用；归还保存的完整权重后 dispatch。nil/零值 Permit 仍为 no-op，禁止复制 Permit。
- 授予后 context 取消不自动归还，避免工作仍在执行却重复分配容量。第一版没有部分 Release、追加令牌或 Permit 拆分。

实现仍是互斥锁保护计数和队列，channel 仅作单请求通知；不是用 channel 中的元素表示可用令牌。运行时不增加第三方依赖、后台 worker 或调度 goroutine。

## 7. 比较边界与选择理由

`x/sync/semaphore.Weighted` 已提供多令牌原子获取；其等待队首容量不足时不放小请求越过，以避免大请求饿死。它没有租户身份和优先级分组。本文复用这种容量保护取舍，增加组和租户两层选择，而不是把原子计数当成 Airlock 独有能力。其当前源码取消竞争会在某些已授予分支归还令牌并返回错误，与 Airlock 的既有契约不同。[官方源码](https://raw.githubusercontent.com/golang/sync/master/semaphore/semaphore.go)

Kubernetes APF 将请求映射到优先级，提供组级并发份额、隔离和组内公平排队，并考虑多 seat 请求；它的组份额是并发资源分配，还支持借用/归还边界。本文只是本地库的请求选择份额，不声称等价实现 APF，也不将其单 apiserver 调度解释为全局分布式额度。[官方文档](https://kubernetes.io/docs/concepts/cluster-administration/flow-control/)

| 候选 | 第一版决定 | 原因 |
| --- | --- | --- |
| 严格优先级堆 | 不选 | 持续高组请求能饿死低组 |
| 容量够就任意绕过 | 不选 | 小请求可饿死大请求 |
| 有限绕过 + aging | 留作实验 | 要增加保护触发阈值/时钟/取消状态，先建立简单正确基线 |
| 按令牌成本的 DRR | 留作不同公平目标的提案 | 只按 n 扣分仍不等于 token-time 公平，需另定义份额和突发约束 |
| 组级固定容量 + 借用 | 留作延迟隔离方向 | 大请求可超过分组容量；借出容量回收和配额碎片需要额外契约 |
| 本方案 | 推荐先实现 | 原子性和不饿死可验证；明确接受 HOL 与按次数公平 |

## 8. 验证与实施拆分

先实现确定性模型和契约测试，再修改本地运行时；不要仅靠睡眠后比较 p99 验证公平。

| 测试层 | 必须覆盖 |
| --- | --- |
| 原子计数 | n=1、n=C、混合 n；并发授予从不超 C；失败零占用；无部分获取 |
| 参数/兼容 | n<=0/n>C、nil ctx、空租户、已取消 ctx 的错误优先级；旧入口等价；默认租户隔离 |
| 释放 | 并发重复 Release 只归还 n 一次；nil/零值安全；ActivePermits 与 InUse 单位正确 |
| 取消竞争 | 授予前/后、队首/中间/尾部、protected 取消；按可控事件屏障固定锁内赢家 |
| 队列接纳 | 三层上限及错误顺序；高组不能用掉低组额度；零等待额度仍可即时授予 |
| 优先与租户 | 全饱和 8:3:1；同组 A/B RR；同租户 FIFO；空组跳过；重入尾部；不追讨信用 |
| 大请求活性 | C=5、protected n=4、持续 n=1；足量释放后必授予；期间新请求无法插队 |
| 非饿死模型 | 有限状态穷举/随机事件序列；持续低组排队时验证最多 11 次其他组选择；单独检查取消消耗槽位 |
| 内存/并发 | 大量租户排空后回收；race；取消与 Release 压力，最后 used/queued 均归零 |

对比矩阵至少包括：当前单令牌 Airlock（仅共同支持的 n=1 场景）、全局 `semaphore.Weighted`、每租户 semaphore + 全局 semaphore 的组合、严格优先级模型（用于展示饥饿反例）、本提案。嵌套 semaphore 固定获取顺序并报告持有局部额度等待全局额度的影响，不给基线隐藏加上公平调度器。

工作负载区分等权/混合权重、短持有/长持有、全部组饱和/低组稀疏、低组大请求/高组小请求、取消风暴。统一容量、到达轨迹、持有时间和随机种子；报告授予次数、等待分位、每组最长选择间隔、拒绝数、令牌利用率、空闲令牌但有等待者的时长、吞吐。各模型不共同支持的队列上限/优先级列为不适用，不能伪装成公平的端到端比较。不能以有限测试“证明永不饿死”，证明靠第 5 节前提和状态机，测试负责查实现偏差。

本地按两个实现阶段交付：原子多令牌及现有租户 RR 的队首保护，以及本分支的优先级配置/组级等待隔离。两者都需同步中英文 README 和 runnable examples，执行 gofmt、`go test ./...`、`go vet ./...`、`go test -race ./...`。后续 driver 复用同样的选择规则与模型测试，网络结果不确定、lease 失效等语义由独立提案定义，不强行套用本地无错误 Release。
