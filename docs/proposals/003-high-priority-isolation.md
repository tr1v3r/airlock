# 高组容量隔离方案与实验契约

状态：组合现有 Airlock 实例的独立实验提案，不增加公共 API。依赖本地优先级实现，
通过独立的后续 PR 提交；合入顺序为优先级实现、容量隔离实验。重要取舍见
[固定容量分区决策](../decisions/004-high-priority-isolation.md)。

## 目标和边界

高组有准入延迟要求。当前共享容量、加权选择、全局受保护队首只能分配选择机会，
不能阻止低组持有者和已选低组大请求延迟高组。本方案隔离这些低组容量依赖；
不承诺任意高组负载下成功准入，也不承诺操作系统调度、CPU、数据库和下游的端到端 SLA。

区分三项指标：成功申请的等待分位数、全体申请的返回时间，以及拒绝/超时比例。
快速拒绝不能算作成功低延迟；只统计成功请求会掩盖超时丢弃。等待期限是取消预算，
不是准时返回保证。取消与授予竞争时，授予先完成仍可能返回成功。

## 固定分区契约

- 总预算 12：高组专用 4，中低组共享 8。数字是实验参数，不是生产推荐值。
- 可信入口把高组送到高组实例，其余送到中低组实例。每个请求只申请一个池。
- 两池各自原子申请、独立排队、独立锁和受保护队首；两个容量之和不超过总预算。
- 中低组继续 3:1 选择；共享对照组采用 H/M/L=8:3:1。本轮负载只生成 H/L，M 为空。
- 高组等待预算 5ms，等待上限 16；低组等待上限 128。两种模式的对应等待额度一致。
- 不借用、不溢出路由、不在两池之后再串共享全局 semaphore。高组容量空闲也不借给低组。
- 请求权重必须不大于目标池容量。高组最多 4，低组最多 8；原来全局可接受的更大请求
  在分区后可能不合法，应由业务拆分可拆任务或改容量划分，不能自动拆分原子申请。
- 每次成功只产生一个 Permit，任务确实停止使用受控资源后才 Release；重复释放无副作用。
- 等待超时返回错误，不重试；获得 Permit 后，申请 context 的取消不回收容量。
  任务执行期限、取消协作、业务失败和重试由调用方管理。
- 启动时创建并固定两个池。切换配置时不能直接建立新池与旧池并行放行，否则会超额；
  需停止旧入口并排空旧 Permit，或另行设计跨代预算。

## 验收方法

确定性测试使用同步信号及有期限的状态屏障，验证：低组受保护大请求阻塞共享池高组，
却不能阻塞独立高组；高组自身满载仍会排队/拒绝；取消等待不重试；已持有资源不会因
context 取消而归还；分区权重限制以及释放记账。测试不以毫秒级延迟作为 CI 门槛。

可选真实公共 API 负载，固定同一到达、权重、持有时间轨迹，三个种子、两种适配器：

| 场景 | 验证目的 |
| --- | --- |
| low-flood | 低组小请求在 t=0 突发入队并形成积压，高组后到 |
| low-large | 低组请求权重 8，高组权重 1；共享池队首保护的跨组影响 |
| low-long | 低组小请求长时间持有，检测调度优先级无法回收已持有容量 |
| high-overload | 高组自身突发，展示固定分区可能更早拒绝及成功样本偏差 |
| low-only | 高组没有请求，量化预留空闲和低组吞吐代价 |

模拟任务通过 Sleep 持有 Permit，不代表 CPU/数据库服务时间。报告保留全部成功、拒绝、
超时及调用启动延迟；记录成功等待 p95/p99、全体调用返回 p99、吞吐和调用方可见令牌时间
利用率代理。完整 trace 在测试代码生成，原始结果随报告保存。不用有限实验证明生产 p99。

## 公共 API 决策标准

先验证两实例组合是否足够。只有可信路由、容量总和校验、汇总统计或配置更新确有重复需求，
才考虑统一封装。借用和抢占是额外策略，不附带加入本次方案。功能验收独立于是否增加 API。
