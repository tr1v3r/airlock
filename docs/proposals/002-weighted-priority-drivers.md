# RFC 002：多租户、多令牌与优先级准入

状态：本地阶段 1（多令牌）和阶段 2（优先级组）已在当前功能分支实现，尚不代表本分支合入 `dev` 或发布。
原提案基线为 `dev` 的 `b6c7f62`；现有单令牌入口保持原语义。
driver、租约客户端及真实后端实验仍未实现。

## 建议结论

保留无需外部服务的本地 Airlock，先实现原子多令牌申请与带最低服务份额的优先级分组，再通过可选 driver 支持 Redis 和 PostgreSQL。三种后端必须遵守相同的排队与调度规则；分布式后端额外提供明确的租约生命周期。

原提案由两个独立 worktree 并行设计。当前本地实现覆盖原子多令牌、组加权选择、组内租户轮转、独占等待额度与队首保护，不包含 driver。

## 用户得到什么

| 能力 | 拟定行为 |
| --- | --- |
| 最简单的本地并发限制 | 继续使用 `New(Config)`、`Acquire(ctx)`、`Permit.Release()` |
| 多租户、多令牌 | `AcquireN(ctx, n)` / `AcquireNFor(ctx, tenantID, n)`，一次获得全部 n 个令牌或一个也不获得 |
| 用户分组 | 由可信配置将租户映射到优先级组；不能通过请求参数自行提权 |
| 高优先级优先 | 高组在调度循环中获得更多授予机会，不抢占已执行任务 |
| 低优先级不饿死 | 每组正份额、组内租户轮转、独立等待预算；已选中的大请求不会被小请求无限插队 |
| 多进程共享并发上限 | Redis / PostgreSQL driver 在共享后端维护容量、队列、调度游标和租约 |
| 本地使用无需部署服务 | 本地实现仍为默认路径；不引入 Redis/PG 运行时依赖 |

这里的“优先执行”准确地说是优先准入：Airlock 不启动任务，不控制调用方何时真正运行。严格高优先级独占与持续高负载下低优先级不饿死无法同时保证，因此选定有正份额的加权调度，不提供绝对抢占优先级。

## 必须同时接受的取舍

1. 第一版公平度量为**请求选择机会**，已选请求取消也消耗机会；无此类取消的完整饱和周期才对应授予次数比例。请求权重表示占用容量，不表示付费积分，也不代表 token-time 公平。高组更多次准入，不等于更多总令牌或更短完成时间。
2. 防止大请求饿死需要保护已选队首。空闲令牌不足时暂缓后续准入，可能降低利用率，也可能让高组等待低组的大请求。这是明确的首版策略，不把吞吐最优作为保证。
3. 不饿死针对已被接受的等待请求，并要求持有者最终释放、调度持续推进。任何请求都没有无条件的等待时长上界；有界队列也不等于有界等待时间。
4. 分布式租约到期可以回收逻辑名额，但不能停止失联或暂停后恢复的业务进程。严格限制实际同时执行数量需要业务资源侧验证，不能仅凭 Redis/PG 租约承诺。
5. 分布式调用存在结果未知的网络错误。需要 request ID、幂等重试、状态查询和补偿；不能沿用本地无返回值的 Release 隐藏失败。

## 与 anylock 的关系

参考 `tr1v3r/anylock` 当前检出的 `16153457be5b39d79fae0ec2d58c9ae73a4c1948`：

- 借鉴 core、`driver/memory`、`driver/redis`、`driver/postgres` 与 integration 的模块隔离，以及调用者持有连接的方式。
- 借鉴 owner 校验、网络操作期限、租约丢失通知和错误结果不能授权执行的契约。
- 不直接复用互斥锁的 `TryAcquire` 重试循环作为公平队列；公平性需要共享调度状态。
- 不直接复用“仅接受最大 fencing token”的互斥写入规则；多个并发 permit 可以同时合法，必须按 lease / slot 身份验证。

具体接口参考及适配差异见 driver 子提案。此处引用的是源码快照，不表示依赖 anylock 或复用它的实现已经完成。

## 分阶段交付与退出标准

| 阶段 | 交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1（当前分支实现） | 本地原子多令牌 API、租户轮转队首保护，保持现有单令牌入口 | 权重非法、容量守恒、取消竞态、重复释放及现有兼容测试通过 |
| 2（当前分支实现） | 在本地轮转与队首保护之上增加优先级组 | 确定性调度测试、不饿死条件测试与比较实验通过；记录利用率代价 |
| 3 | Driver 契约与 memory 参考实现，租约客户端 | 契约测试覆盖幂等、结果未知、续期/过期和取消；与本地共用调度决策模型 |
| 4 | PostgreSQL driver | 真实 PG 多进程及故障测试通过，事务锁顺序和崩溃恢复可复现 |
| 5 | Redis driver | Lua 原子状态转换、Cluster 同槽、多客户端故障测试通过；文档明确部署及持久化限制 |
| 6 | 中英文说明、可运行示例、完整基线与模块 CI | 本地和远端示例均可运行，各模块可独立消费，不依赖本地 replace |

建议先 PG 后 Redis：共享资源行事务锁便于审查整个状态转换，先固定协议，再移植成受执行时长约束的 Lua 操作。这是实现顺序，不是宣称 PG 在任意部署下都提供更强保证。

每一阶段独立 PR 到 `dev`。后续实现须在新的功能 worktree 进行，主检出继续保持干净。此提案不自动授权发布版本或引入未评估的依赖。

## 比较与验收

不以“比 semaphore 更快”作为目标。基线包含 `x/sync/semaphore.Weighted` 全局 FIFO、租户级加全局两层 semaphore、当前 Airlock 和新调度器。分别测相同权重退化、大小请求混合、高组持续满载、稀疏低组及取消风暴；报告等待分位数、最大等待、授予份额、利用率与吞吐，不将小样本最大值写成生产 p99。

分布式测试另测单资源竞争、不同资源隔离、结果丢失、客户端崩溃、服务重启和租约过期；不得把后端逻辑名额测试宣称为业务执行不会重叠的证明。子提案给出详细测试矩阵。

提案验收是契约与测试计划完整、跨文档一致；实现验收才运行代码测试和真实后端故障实验。本 RFC 的本地比较结果单独记录在[优先级实验报告](002-priority-experiment-results.md)，分布式后端尚无实现测量结果。
